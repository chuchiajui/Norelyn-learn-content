# Offline public pair validation

Run with Node.js 20 or newer; no dependencies or network access are needed:

```sh
npm test
npm run validate
```

`validate` reads only this repository's `articles/` directory. Absent or empty
directories pass. Failures print per-file diagnostics and exit nonzero; the
validator never writes files or follows symlinks. Synthetic test fixtures live
under `test/fixtures/`, never in the public article namespace.

## Mirrored contract

Source: `chuchiajui/Norelyn-learn`, branch
`feat/learn-content-contracts-20261024`, commit
`34e7b87d6faff93cf21cc5db428cd397afbd55ad`, specifically `publication.ts`,
`contracts.ts`, `public-file-reader.ts`, and `publication-reader.ts` under
`apps/api/src/content/`, plus `tests/publication.test.mjs` and
`docs/owner-publication-v1.md`. This is source compatibility, not a live-service claim.
The compared branch `devin/1795234799-learn-public-projection` at
`c5102429416de820e93749983228bb18a7c9eb57` has identical Git blobs for all four
contract modules above; the branches diverge elsewhere, not in these pair rules.

Checks include:

- Only `articles/art_<32 lowercase hex>/rev_<32 lowercase hex>.md` and `.json`
  pairs; no orphan files, unexpected files/directories, or symlinks.
- Exactly the 12 public manifest keys emitted by Learn; types, required fields,
  positive safe-integer source revision, article/submission/path identity, and
  revision equal to `rev_` plus the first 32 characters of the SHA-256 hash.
- Manifest text must equal `JSON.stringify(parsedManifest, null, 2)`, with no
  trailing newline, matching `admin-export-route.ts` at the mirrored commit.
  This rejects duplicate keys (including overwritten private values), alternate
  escaping, and extra formatting. This is deliberately stricter than Learn's
  public reader and `VerifiedPublicCommitStore`: both parse JSON, and the latter
  compares reserialized objects rather than raw manifest text. The unused
  `GitHubPublicationStore` writer emits compact JSON; this validator targets the
  manual owner export, not that writer's formatting.
- Learn publication limits: title 200, summary 1200, Markdown 100000,
  tags at most 12 of length at most 40, videos at most 8 matching
  `[A-Za-z0-9_-]{11}`, valid category or null, parseable approval date of length
  at most 40. Title and Markdown must be nonblank. Lengths are JavaScript UTF-16
  code units, not Unicode code points. Reader limits also apply: 400000 raw bytes
  per file, fatal UTF-8 decoding, and 20000 decoded manifest code units.
- Canonical content digest: SHA-256 of UTF-8 `JSON.stringify` of fields in this
  exact order: `title`, `summary`, `bodyMarkdown`, `categoryId`, `tags`,
  `youtubeVideoIds`. The public reader reconstructs exactly these fields, so
  the hash **is derivable from the pair** for this contract. It is not a hash
  of Markdown alone. No trimming, newline conversion, or reformatting is done.
  Decoding uses Learn's TextDecoder behavior (including stripping a leading
  UTF-8 BOM); it is not a byte-for-byte comparison to a private D1 snapshot.
- Heuristic privacy rejection in Markdown and each decoded manifest key/string
  value (recursively, including arrays): emails,
  private user identifiers, GitHub token forms, JWT-like strings, signed URL
  parameters, private filesystem paths, and forbidden ownership/review fields.
  Diagnostics name the rule, not the matching sensitive value.

The publication/export and public reader rules overlap but are not identical:
the reader does not itself enforce exact keys or the source revision field;
this validator enforces the export's exact schema too. Draft normalization
(e.g. category length 64, tag deduplication) is not reapplied to frozen exports.
Arbitrary extra content fields or a different content property order could
produce an export digest the public reader cannot reconstruct; those fail here,
as they do in that reader. Source revision and approval time cannot be proven
authentic from this pair alone.

The fixture was generated by fetching that commit's `publication.ts` outside
this repository and executing its `contentDigest`, `prepareApprovedPublication`,
and `publishedPaths` functions using Node 22's TypeScript transform. All inputs
are synthetic (zero-filled submission ID, test-only title and video ID); no D1
record, person, actual video, approval, or publication is represented.
Its manifest uses the manual export's two-space serialization without a trailing
newline (the initial fixture generator's added newline has been removed).

## Not proof of publication or safety

Passing is **not approval, not D1 publication, and not live**. This tool cannot
check private approved snapshots, reviewer authority, Git commit pinning, D1
allowlisting, licensing, consent, malicious Markdown rendering, or completeness
of privacy detection. It is not an HTML sanitizer or a comprehensive secret
scanner. Human privacy/license review and Learn's explicit publication checks
remain required. No workflow, deployment, or network publication is installed.
